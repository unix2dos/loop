## 教学式轨迹界面：第一轮讨论（2026-09-17）

状态：用户要求先做双向钢人论证，并用 grill-with-docs 访谈。以下区分已明确的目标、核实的事实与待决策事项；界面方案尚未确认，未开始实现。

### 用户明确的方向

- 首要目标是方便新手学习 Agent，产品定位为教学式 Agent。
- 平铺事件和耗时时间轴缺少关系感，希望看清一次运行的整体过程。
- 希望任务对话与轨迹在同一界面中查看，减少来回切换。

- Mermaid 或 HTML 图表是候选表现方式，尚未决定图形库、布局或交互。

### 当前事实与边界

- 用户在本地 WebUI 提交任务，Go 服务运行 Agent 并调用配置的模型 API；当前在线模型不在本机推理。
- 每次提交创建新的 Run，上下文重新建立为 system + user。网页“对话”仅呈现当前任务及最终回答，尚无跨提交的连续会话或围绕轨迹的教学问答。
- 轨迹每 650 ms 轮询更新；没有 token 流、实时暂停、单步执行或中断恢复。历史逐步查看与真实执行暂停是不同能力。
- 本地已有 run.json、trace.jsonl、session.jsonl。事件 ID、模型请求序号、tool_call_id、真实输入输出及源码快照可用于建立有证据的关系。
- 例：运行 f48bc428ac6544729f1ce2b1810d8653 中，e007 提出错误路径，e009 返回 tool_rejected，e011 的 input.messages[5] 包含同一调用 ID 的错误回执，且该次响应提出正确路径。可证明数据传递和后续响应内容，不能据此重建模型内部推理。
- 图中节点与本地文件的定位可由现有记录派生；事件可用 run.id + event.id 标识。图中一个教学节点也可能聚合多个事件，不能假定节点与日志行永远一一对应。

### 双向论证的核心

- 支持：学习者目前需要自行把时间相邻的日志串成机制；显式展示调用、回执和下一次模型请求的关系，并与任务及原始证据联动，能直接针对已经出现的理解卡点。
- 反对：完整图、聊天、JSON 和源码同时展开可能增加理解负担；漂亮连线也可能错误暗示模型直接执行、同批工具之间发生新模型请求、固定未来路线或已经知道模型内部推理。连续任务对话与教学问答还会改变产品及会话边界。
- 真正分歧是先让学习者掌握哪些关系、默认展示多少细节、输入框承担什么职责，以及怎样验证学习效果。渲染库选择应在这些决策之后。

## 重新评估全 TypeScript（2026-09-18）

状态：用户提出“把语言全换成 ts，省的未来再次重写”，要求先做双向钢人论证，再用 grill-with-docs 访谈。迁移尚未决定；本节是讨论记录，不取代 ADR-0001，不构成实施授权。

### 已核实的事实

- ADR-0001 选择 Go 内核与 TypeScript 网页，首要依据是作者阅读 Go 最顺、独立理解内核优先；它明确不预设未来必须迁移为全 TS。
- 当前 CONTEXT.md 将 Loop 定位为面向新手的 Coding Agent；代码已有独立 Go 修复练习、受限写入和容器测试。产品能力已超过最初的只读工作台，但这不自动证明旧选型失效。
- TypeScript 当前只用于网页；Agent 循环、模型适配、HTTP 服务、文件工具、会话与持久化均在 Go。没有现成 TS 内核可直接启用。
- 全 TS 迁移还涉及源码证据：storage.go 使用 Go AST 提取函数源码及行号，并关联构建摘要；历史记录应继续保留当时的真实源码。
- testdata/loop-cases.json 已被 Go 与 Python 对照检查使用，可复用为语言中立的行为基线；它不覆盖全部后续 Coding 能力。
- 当前模型调用读取完整 JSON，网页轮询；没有 token streaming 或用户取消路由。现有 context 检查和工具执行超时不等同于这些产品能力。

### 双向论证

- 支持：若 TS 已成为作者明确的长期技术方向，趁运行内核仍较小统一语言，可以降低后续跨语言维护与阅读成本，让新增能力和学习成果持续积累；等待当前 Go 真正受阻才迁移，可能错过成本较低的时机。
- 反对：未来必然改 TS 仍是待证明的前提；立即迁移是确定支出，未来迁移只是可能支出。统一语言不能消除会话、权限、持久化或产品边界变化带来的重构，且需要重新验证现有行为与源码证据。
- 真正分歧：长期目标是否已确定为 TS、Go 的当前可理解性是否仍是首要约束、具体未来需求是否带来语言限制，以及现在迁移相对继续验证产品的机会成本。
